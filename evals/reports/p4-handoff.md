# P4 -> P5 handoff: what was built, what broke, what is still owed

P4 set out to build the ability to measure before building the thing to be measured: a labeled dataset, a cost-capped way to run a model against it, and the math to score what comes back. That ability now exists on `main` across four commits, reviewed and merged, with one deliberate hole in the middle of it: no model was ever called, because the user chose not to spend the money in this phase. Everything below is written with that hole kept visible, because the most dangerous thing this document could do is let a reader mistake infrastructure for evidence.

## What was built, and why each piece exists the way it does

The dataset came first because the criteria had to be committed before any label existed  -  D10's whole point is that entries admitted after the fact can be admitted because they help the numbers. `evals/dataset/build.py` is therefore deterministic and LLM-free by construction: 42 synthetic sink files, each carrying a vulnerable twin and a mitigated twin, plus 19 Flask findings harvested from the pipeline's own P3 output at a pinned SHA, every entry stamped with finding, repo SHA, ground truth, a rationale a stranger could audit, provenance, and labeler. The synthetic twins exist because the corpus triability work showed only 19 real Python findings were adjudicable  -  not enough to measure anything  -  and the Flask subset exists so the dataset still touches genuine scanner output from a real codebase.

The provider adapter exists because the original plan called Anthropic directly and the phase switched to the OpenRouter gateway for cost and model flexibility. The switch is deliberately narrow: one interface, pinned `("anthropic",)` routing with fallbacks off, temperature and model recorded into every report. The pin matters because a metric that moves after a silent routing change is not a measurement of anything this project did, and the stamp exists so that failure mode is visible rather than silent.

The scoring module exists as pure math with no network, no prompts, no model access, because the alternative  -  scoring tangled into the runner  -  would mean the numbers could only be produced by spending money, and could never be tested without doing so. `score_subset` and `score_all` join entries to outcomes by id and raise on any mismatch rather than dropping rows, because a harness that silently drops findings is committing the one sin this project names explicitly. Each provenance scores alone and nothing is ever pooled, because D13 assumes the public benchmarks are contaminated and the private holdout is the number that counts.

The baseline prompt and runner exist to be D12-genuine: the same context bundles, the same output schema with the safety rule enforced in code rather than prose, and a prompt written to win rather than to lose gracefully. If it matches the future four-agent pipeline, the pipeline gets cut  -  that only means something if the baseline was honestly trying. Rendering lives in `sift.agents.baseline.render_baseline_prompt`, shared by runner and test, so the path Hermes reviews is the path that spends money.

## Every bug review caught, with its root cause

The dataset went through three review rounds with two rejections (round 3 passed), and the shape of the failures is the real finding of this phase. Round 1 found the labels sitting directly inside the model-visible text: `# finding: TP` comments, `tp_`/`fp_` function names, a docstring announcing the pair  -  all inside the untrusted block the adjudicator reads. Hermes proved it not by reading the builder's intent but by running the actual P3 context builder on `tls_verify_false.py:5` and reading `def tp_post(...): ... # finding: TP` back out of the model-visible output. The root cause was architectural, not typographic: labels lived in the same source the context builder reads, so every field of that source was a potential oracle. The same round found that "zero LLM calls enforced by test" was a false claim  -  the test guarded only the context builder, and nothing watched the dataset builder at all. The fix relocated markers to build-time-only parsing (stripped from written files), neutralized docstrings, and extended `tests/test_no_llm.py` with an import sweep plus a socket-disabled full build run over `build.py`.

Round 2 is the more instructive failure, because it was a fix that closed the named channel without establishing the invariant. Function names were neutralized to `alpha_`/`beta_`  -  but the name assignment still followed the label, so `alpha_` was true-positive in all 42 files and the oracle survived untouched, now contradicting the fix's own docstring. Independently, 27 pairs carried different rule IDs per twin with mitigation-named false-positive sides, leaking the label through the rule name for 22 of 58 false-positive entries with zero code reading required. Both times the root cause was the same: the repair targeted the literal leak Hermes had demonstrated rather than the property that had to hold  -  names and rule IDs must correlate with something other than ground truth. The durable fix asserts the invariant in `tests/test_no_llm.py` on every run: no marker comments or label-named functions in written snapshots, twins sharing one rule, `alpha_` true-positive in roughly half the files (17 of 42 at pass time, verified programmatically). Round 3 passed on those terms.

The provider switch was rejected once, and the lesson is about what rides along with an unrelated change. The swap carried a silent Adjudicator downgrade from the pinned Opus generation to an older one, with no comment and no cost justification  -  same price on the gateway  -  and because the baseline model resolves through the same `ModelId.OPUS`, it would have silently re-anchored the eventual step-5 baseline too. The decision to restore was the lead's, grounded in the project's explicit rule against downgrading the safety-critical stage to save money, with no saving on offer. The same round caught a second, quieter source of drift: the routing pin lived in two untied places, and the report's stamp could have kept claiming one provider while the adapter dialed another. Both are the same bug class  -  a change whose blast radius exceeds its description  -  and the defense is the same in both cases: review greps the tree for the stale model string and adversarially live-patches the provider default to prove the stamp assertion actually fires.

The pilot infrastructure was rejected once, for a bug that would have spent the phase's entire budget on nothing. The baseline template double-escaped its outer JSON braces while `str.format` strips only one level, so the model would have been shown literal `{{ }}` around the output example  -  and a literal-following model echoes them back, `json.loads` fails on every finding, and 103 paid calls produce zero valid adjudications. Nothing caught it because nothing rendered the prompt end to end; the gate was green and the template was broken. The fix extracts rendering into the shared function the runner actually calls and tests it through the real context builder, plus gitignores the raw run outputs that would otherwise commit analyzed source on first execution. Round 2 passed when Hermes independently re-rendered three real dataset entries through the real builder and confirmed zero double-braces survived  -  re-deriving the value rather than trusting the new test's claim, the same pattern as every prior round. One thread runs through all seven rejections: every round-1 defect smuggled a label or a config value into a channel nobody was checking  -  source content, a template string, a second untied config field, a docstring's own claim about itself  -  and every catch came from re-deriving the actual value instead of trusting the written claim about it. That is the pattern to carry into P5 review. The general rule this phase kept re-learning: never trust a path no test walks  -  the builder's intent, the template's appearance, the stamp's claim are all untested assertions until something executes them.

## What is simplified, missing, or owed

Two provenance classes are empty and the report does not hide it. There is no OWASP or Juliet surface because the builder reads only Python and those suites offer nothing honest to label in it; there is no CVE-fix subset because no fix commit could be verified without network access. The eventual live run therefore measures hand-labeled volume plus a 19-finding single-repo Flask check  -  a pilot baseline, sufficient to shake down the machinery and calibrate the safety metric, but not the D12 baseline the multi-agent thesis must clear. Filling the empty classes needs a second language builder or network-verified fix SHAs, both explicitly future work.

No live scoring exists. The scoring module's tests prove it computes correctly over synthetic outcomes, including the all-escalate control and the false-suppression mutation, but no model output has ever entered it. The content-hash result cache is specified but unbuilt, deferred to P5's orchestrator as designed  -  a re-run today costs the full estimate again.

Blocked on one thing only: the step-5 live run, awaiting a future decision to spend roughly $2.58 against the $5.00 cap. Nothing technical stands in the way. Set `SIFT_API_KEY`, check out Flask at `d318b68`, run `uv run python evals/pilot/run_baseline.py --flask <checkout>`, score the rows, render the report.

## What P5 needs to know

The contract between runner and scorer is `ModelOutcome.from_run_row` in `src/sift/eval/scoring.py`: one row per entry id, `verdict` as a `Verdict` name, `completeness` as a `ContextCompleteness` name or null for rows that never built context, `schema_valid` bool (failures still escalate as `NEEDS_HUMAN_REVIEW`  -  never dropped), `cost_usd` float, `latency_ms` int. Malformed rows raise `ValueError` rather than scoring as something they are not. Raw rows live gitignored under `evals/pilot/runs/` (`run-a.jsonl`, `run-a-injection.jsonl` kept separate and never pooled, `run-b.jsonl` for the control). Prompt rendering goes through `sift.agents.baseline.render_baseline_prompt`  -  any P5 prompt work should follow the same pattern of one shared render function with a test that walks the real path, because this phase demonstrated twice that the untested path is the broken one. And the standing practice from every phase still holds: run the deterministic component against real input, treat a suspiciously good number as a bug report first, and never tune the eval to agree with the architecture.
